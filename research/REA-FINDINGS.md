## Runtime follow-up boundary

A further attempt to exercise the actual tutorial found a concrete tool limitation: the installed REA `browserScenarioActionSchema` admits locator-based click, fill, press, select, check and waits; it has no pixel coordinates, mouse movement or drag action. The actual game is canvas-rendered, and the welcome Continue target is at the lower right rather than the canvas center. E3 and E4 therefore do not corroborate play execution. An attempted isolated headless Edge/CDP launch for a coordinate-based Playwright probe was rejected by automatic execution policy: `approval required by policy, but AskForApproval::Granular.sandbox_approval is false`. There was no available user approval prompt. This was not bypassed. Consequently, original passing, running and downs are established from captured shipped-code branches only, not from runtime gameplay.

## Reconstruction guidance and unanswered work

Preserve the offense-first decision loop: read routes, choose a target, trade a lob's airtime against a bullet's lower interception window, exploit blocking, run after catch, earn first downs, score, then resolve the opponent possession. Behind-offense projection and continuous analog movement change spatial readability; receivers need distinct labels and route previews, and the target must remain visible while moving the QB. The new game should own all route geometry, simulation constants, names, art, UI and audio.

The actual-game study is deep at the inspected shipped-code branch level but only partial overall. It does not certify full behavior parity. Missing original-match runtime play, complete route generation, all difficulty tuning, hidden probabilities, full franchise rules and controller hardware validation must remain explicit. The reconstruction's own feature checklist and tests must be reported separately from these original-game findings.
